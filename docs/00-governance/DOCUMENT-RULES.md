# Document Rules

## 1. Purpose

本文档定义 `toast` 的文档写作、目录归属和同步规则。目标是让文档适合人类阅读、AI 执行和长期维护。

## 2. Scope

当前范围：

- 根目录协作文档，例如 `AGENTS.md`、`TODO.md`、`README.md`
- `docs/00-governance/` 长期治理规则
- 未来按需新增的需求、设计和运行文档

不在范围内：

- 不替代具体功能设计
- 不替代代码风格工具配置
- 不记录已完成任务清单

## 3. Directory Rules

当前固定目录：

- `docs/00-governance/`：稳定治理规则，例如文档规则和 TODO 规则。

未来按需新增目录：

- `docs/10-requirements/`：业务需求和产品规则。
- `docs/30-designs/`：专项方案、一次性设计和复杂任务说明。
- `docs/40-readiness/`：上线、发布和运维准备。

不得为了占位创建空目录。目录只有在存在真实文档时才新增。

## 4. File Naming

- 文档文件名使用大写英文。
- 单词之间使用 `-` 连接。
- 文件名不得使用中文或空格。
- 治理规则文件固定使用 `*-RULES.md`，例如 `TODO-RULES.md`。

## 5. Language Rules

- 文档说明内容使用中文。
- 代码、命令、路径、配置键、包名、类名、函数名和字段名保留英文原文。
- 不为了“纯中文”翻译代码概念。
- 不为了“纯英文”把业务说明改成英文。

## 6. Content Rules

- 文档必须清晰、明确、可执行。
- 治理文档只沉淀稳定规则，不记录讨论过程或完成清单。
- `TODO.md` 只记录未关闭任务，不记录完成历史。
- 完成记录保留在 commit 或 PR 中。
- 同一规则只放在一个权威位置，避免多处重复且表述不一致。
- 临时方案进入 `docs/30-designs/`；稳定后再收敛到 `docs/00-governance/`。

## 7. Rule Expression

- 使用确定性表达。
- 已确认规则直接写成约束。
- 避免用“建议”“可考虑”“视情况”“后续再看”等不确定措辞表达规则。
- `Open Items` 为空时固定写 `无`。

## 8. Document Sync Rules

改动完成前必须检查是否需要同步文档：

- 改执行队列或任务生命周期：同步 `TODO.md` 和 `docs/00-governance/TODO-RULES.md`。
- 改文档目录、命名、语言或治理口径：同步本文档。
- 改仓库级协作入口：同步 `AGENTS.md`。
- 未来改需求口径：同步 `docs/10-requirements/` 中对应文档。
- 未来改专项方案或一次性执行计划：同步 `docs/30-designs/` 中对应文档。

仅实现既有口径且不改变规则时，不为“看起来完整”顺手修改无关文档。

## 9. Open Items
