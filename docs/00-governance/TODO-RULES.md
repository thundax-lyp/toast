# TODO Rules

## 1. Purpose

本文档定义根目录 `TODO.md` 的写入、执行和关闭规则。目标是让 `TODO.md` 成为清晰、可审阅、可执行的未关闭任务队列。

## 2. Scope

当前范围：

- 根目录 `TODO.md`
- 任务分类、写入格式、执行许可和关闭规则
- 任务完成后的测试、文档和提交收口检查

不在范围内：

- 不替代需求文档、设计文档或长期治理规则
- 不记录已完成任务清单
- 不承载低置信度观察、灵感或长篇方案

## 3. TODO Types

`TODO.md` 固定承载三类未关闭事项：

- 宏观任务：目标值得推进，但尚未拆成可执行步骤。
- 执行任务：范围、动作和验收点已经明确，可以直接执行。
- 待讨论项：需要人工先做决策，不得直接执行。

宏观任务和待讨论项不是执行许可。未经人工确认的拆解任务固定放入 `待审阅任务项`。

## 4. File Structure

`TODO.md` 固定使用以下结构：

```markdown
# TODO List

## 说明

- `TODO.md` 是未关闭执行队列，不是完成清单。

## 当前任务项

- [ ] `scope`：任务标题
  - 范围文件：精确文件路径
  - 处理动作：一句话说明要做什么
  - 验收点：可检查的完成结果
  - 重要度：N/10

## 待审阅任务项

## 待讨论项

- [ ] 需要决策的问题
  - 关联任务：任务名或范围对象
  - 决策要求：需要人工确认的具体问题
  - 重要度：N/10
```

## 5. Writing Rules

写入 TODO 前必须判断：

1. 任务是否值得进入执行队列。
2. 任务是否能用一句话说明目标。
3. 任务是否能归类为宏观任务、执行任务或待讨论项。
4. 任务是否有明确下一步动作、拆解依据或决策问题。
5. 任务是否不是低置信度观察项。

执行任务必须包含 `范围文件`、`处理动作`、`验收点` 和 `重要度`。一个执行任务只表达一个主动作；如果动作或验收点包含多个无关判断，必须拆分。

## 6. Execution Rules

- 只执行 `当前任务项` 中已经明确的执行任务。
- 不执行 `待审阅任务项`，除非人工明确确认。
- 不执行 `待讨论项`，先完成决策。
- 执行时优先限定在 `范围文件` 内。
- 发现任务边界错误时，先重写 TODO，再继续执行。

## 7. Closure Rules

任务完成后固定处理：

- 完成整项：删除该 TODO。
- 完成部分：收窄为剩余未完成内容。
- 发现拆分错误：重写为正确任务。
- 待讨论项完成决策：删除待讨论项；如仍需执行，新增明确执行任务。

已完成任务不得在 `TODO.md` 中打勾长期保留。

## 8. Closeout Checks

收口前必须检查：

1. 当前目标是否达到可检查状态。
2. 是否还有剩余范围需要留在 `TODO.md`。
3. 行为变化是否需要补充或更新测试。
4. 规则、命令、目录或口径变化是否需要同步文档。
5. 当前改动是否能用一句话解释。

代码、测试、文档和对应 TODO 清理应尽量放在同一个语义闭环中。

## 9. Commit Guidance

提交信息优先使用：

```text
Type(scope): 中文说明
```

示例：

- `Docs(governance): 初始化 TODO 执行队列规则`
- `Feat(core): 增加内容处理入口`
- `Fix(config): 修正环境变量示例`
